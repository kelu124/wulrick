# CH569 + RP2350B: USB 3.0 SuperSpeed Data Exfiltration

*Context: The FT2232H (see `FT2232H.md`) solves the USB Full Speed bottleneck and gives ~40 MB/s over USB 2.0 HS via its 8-bit parallel FIFO. The CH569 (WCH RISC-V, native USB 3.0 SuperSpeed) provides a CDC-ACM composite device and a USB3 SS bulk endpoint — all through a single USB-C connector with no proprietary driver on the host side. CH569's HSPI peripheral is a genuine parallel bus (8/16/32-bit data width, up to 120 MHz) capable of ~154 MB/s demonstrated throughput — see the [Parallel HSPI section](#ch569-hspi--parallel-bus-mode) for details. The simple path documented here uses the HSPI in a reduced serial configuration (~9 MB/s), which is adequate for pulsed ultrasound at ≤ 400 Hz PRF.*

---

## When to use CH569 vs FT2232H

| Scenario | FT2232H | CH569 (serial SPI) | CH569 (parallel HSPI + PIO) |
|----------|---------|-------------------|------------------------------|
| Raw RF at 200 Hz PRF (3.2 MB/s) | ✓ 12× headroom | ✓ 2.3× headroom | ✓ 15× headroom |
| Raw RF at 400 Hz PRF (6.4 MB/s) | ✓ 6× headroom | Tight (1.46×) | ✓ 7× headroom |
| Full 65 Msps continuous (~130 MB/s) | ✗ | ✗ | ✓ (~50–75 MB/s ceiling) |
| CDC-ACM serial + data on one cable | ✗ Needs second channel | ✓ composite | ✓ composite |
| Linux host, no custom driver | Needs libftdi install | ✓ | ✓ |
| RP2350B GPIO count | 4 (PIO) | 5 | 13 |
| Firmware complexity | Low | Medium | High |
| Higher data throughput (> 40 MB/s) | ✗ | ✗ | ✓ (PIO 8-bit HSPI) |

For ultr4rick at 200–400 Hz PRF, any of the three paths works. The serial SPI path is the simplest and sufficient. The parallel HSPI path is the upgrade route when the SPI ceiling matters — see [CH569 HSPI — Parallel Bus Mode](#ch569-hspi--parallel-bus-mode).

## Hardware Interface: RP2350B ↔ CH569

### Bus selection

| Bus option | Speed | Pros | Cons |
|-----------|-------|------|------|
| **CH569 HSPI serial mode** | 7.5–9.375 MB/s | Hardware SPI1 + DMA on RP2350B; 5 GPIO pins; simplest firmware | Lower throughput ceiling than FT2232H parallel FIFO |
| **CH569 HSPI 8-bit parallel mode** | ~50–75 MB/s | Native CH569 DMA; RP2350B PIO; >40 MB/s ceiling | 13 GPIO pins; PIO handshake firmware; see [Parallel HSPI section](#ch569-hspi--parallel-bus-mode) |
| UART | 12 Mbps max | Trivial wiring | Far too slow for bulk data |

**This section documents the serial path.** CH569 HSPI supports both serial (1-bit) and 8/16/32-bit parallel modes. Serial mode uses a single MOSI line driven by RP2350B hardware SPI1, adequate for ≤ 400 Hz PRF. For the full parallel HSPI interface, see the dedicated section below.

### Pin mapping

RP2350B SPI1 primary pins: SCK = GPIO 10, TX = GPIO 11, RX = GPIO 12, CSn = GPIO 13. GPIO 12 and 13 are repurposed as plain GPIO (manual CS and ACK input) so that the hardware SPI peripheral handles clock generation and FIFO feeding on GPIO 10–11 only.

| Signal | RP2350B GPIO | SPI1 peripheral role | CH569 Pin | Direction | Init call |
|--------|-------------|---------------------|-----------|-----------|-----------|
| HSPI_CK | **GPIO 10** | SPI1_SCK (primary) | PA14 (HSPI_CK) | RP→CH | `gpio_set_function(10, GPIO_FUNC_SPI)` |
| HSPI_MOSI | **GPIO 11** | SPI1_TX (primary) | PA13 (HSPI_RX) | RP→CH | `gpio_set_function(11, GPIO_FUNC_SPI)` |
| HSPI_CS | **GPIO 12** | SPI1_RX repurposed → GPIO out | PA12 (HSPI_CS) | RP→CH | `gpio_init(12); gpio_set_dir(12, GPIO_OUT)` |
| HSPI_ACK | **GPIO 13** | SPI1_CSn repurposed → GPIO in | PA15 (HSPI_ACK) | CH→RP | `gpio_init(13); gpio_set_dir(13, GPIO_IN); gpio_pull_down(13)` |
| RESET# | **GPIO 14** | SPI1_SCK alt (unused) → GPIO out | NRST | RP→CH | `gpio_init(14); gpio_set_dir(14, GPIO_OUT)` |

**Why manual CS (GPIO 12) instead of hardware SPI1_CSn (GPIO 13)?**
Hardware SPI CSn on RP2350B deasserts between 8-bit frames in certain configurations and cannot be guaranteed to stay asserted across a DMA burst without explicit configuration. Manual CS is unambiguous: assert before writing the DMA source address, deassert in the DMA completion ISR after the SPI shift register drains. GPIO 13 (the hardware SPI1_CSn pin) is repurposed as the ACK input, which is exactly what we need it for.

**Voltage:** RP2350B and CH569 both operate at 3.3V I/O. No level shifting required.

**Series termination:** 33Ω on CK and MOSI at RP2350B end for PCB traces > 5 cm.

**CH569 crystal:** USB 3.0 requires precise clock. CH569 needs a 30 MHz external crystal on XI/XO pins (or 25 MHz depending on variant — verify against CH569 datasheet). The internal RC oscillator is not adequate for USB3.

## Firmware Split

| Responsibility | Runs on | Mechanism |
|---------------|---------|-----------|
| ADC capture, ping-pong DMA | RP2350B Core 0 | SPI DMA, interrupt on complete |
| Hilbert / envelope (optional) | RP2350B Core 1 | CMSIS-DSP (see `M33FPUHILBERT.md`) |
| Push 16 KB block to CH569 | RP2350B SPI master | DMA → SPI TX FIFO; wait HSPI_ACK high |
| Receive block from RP2350B | CH569 HSPI slave | HSPI DMA → SRAM ping-pong |
| USB3 bulk IN to host | CH569 USB3 controller | DMA from SRAM, EP4, 1024 B packets |
| USB3 CDC-ACM serial | CH569 USB3 controller | EP1/EP2 bulk + EP3 interrupt |
| USB enumeration / EP0 | CH569 USB3 stack | Class request handler in firmware |

RP2350B is not aware of USB at all — it pushes data over SPI and waits for ACK. The CH569 handles everything USB-facing.

### 1. USB3 composite descriptor

The device enumerates as a composite device using IAD. Three interfaces:
- **Interface 0:** CDC communication (control, notification EP3 interrupt IN)
- **Interface 1:** CDC data (EP1 bulk OUT + EP2 bulk IN)
- **Interface 2:** Vendor bulk data (EP4 bulk IN — 16 KB frames from RP2350B)

SuperSpeed requires a BOS descriptor and a SuperSpeed Endpoint Companion Descriptor after each non-zero endpoint descriptor.

#### Device descriptor

```c
const uint8_t USB3_DeviceDescriptor[18] = {
    0x12,        /* bLength */
    0x01,        /* bDescriptorType: Device */
    0x00, 0x03,  /* bcdUSB: 3.00 */
    0xEF,        /* bDeviceClass: Miscellaneous — required for IAD composite */
    0x02,        /* bDeviceSubClass */
    0x01,        /* bDeviceProtocol: IAD */
    0x09,        /* bMaxPacketSize0: 2^9 = 512 B (SS control EP; coded as exponent) */
    0x86, 0x1A,  /* idVendor: 0x1A86 WCH — change for production */
    0x69, 0x55,  /* idProduct: 0x5569 — assign per project */

    0x01,        /* iManufacturer */

    0x00,        /* iSerialNumber */
```

#### Configuration descriptor (115 bytes, all interfaces and SS companion descriptors)

```c

 * Layout (115 bytes):
 *   Config(9) + IAD(8)

    /* Configuration Descriptor */
    0x09, 0x02, 0x73, 0x00,   /* wTotalLength = 115 = 0x73 */
    0x03,                      /* bNumInterfaces: 3 */
    0x01, 0x00, 0x80, 0xFA,   /* bConfigVal, iConfig, bmAttr bus-pwr, bMaxPower 500mA */

    /* IAD: bind interfaces 0–1 as CDC-ACM */
    0x08, 0x0B, 0x00, 0x02, 0x02, 0x02, 0x01, 0x00,

    /* Interface 0: CDC Communication */
    0x09, 0x04, 0x00, 0x00, 0x01, 0x02, 0x02, 0x01, 0x00,
    /* CDC Header FD */
    0x05, 0x24, 0x00, 0x10, 0x01,
    /* CDC Call Management FD (no call mgmt, data on If1) */
    0x05, 0x24, 0x01, 0x00, 0x01,
    /* CDC ACM FD (line coding + control state) */
    0x04, 0x24, 0x02, 0x02,
    /* CDC Union FD (master=If0, slave=If1) */
    0x05, 0x24, 0x06, 0x00, 0x01,
    /* EP3 IN Interrupt: CDC notification, 64 B, 10 ms */
    0x07, 0x05, 0x83, 0x03, 0x40, 0x00, 0x0A,
    /* EP3 SS Endpoint Companion */
    0x06, 0x30, 0x00, 0x00, 0x40, 0x00,  /* wBytesPerInterval=64 for interrupt */

    /* Interface 1: CDC Data */
    0x09, 0x04, 0x01, 0x00, 0x02, 0x0A, 0x00, 0x00, 0x00,
    /* EP1 Bulk OUT: CDC data host→device, 1024 B SS max packet */
    0x07, 0x05, 0x01, 0x02, 0x00, 0x04, 0x00,
    /* EP1 SS Endpoint Companion */
    0x06, 0x30, 0x00, 0x00, 0x00, 0x00,
    /* EP2 Bulk IN: CDC data device→host */
    0x07, 0x05, 0x82, 0x02, 0x00, 0x04, 0x00,
    /* EP2 SS Endpoint Companion */
    0x06, 0x30, 0x00, 0x00, 0x00, 0x00,

    /* Interface 2: Vendor bulk (data exfiltration) */
    0x09, 0x04, 0x02, 0x00, 0x01, 0xFF, 0x00, 0x00, 0x00,
    /* EP4 Bulk IN: 16 KB frames to host */
    0x07, 0x05, 0x84, 0x02, 0x00, 0x04, 0x00,
    /* EP4 SS Endpoint Companion (bMaxBurst=15: 16 packets × 1024 B = 16 KB per burst) */
    0x06, 0x30, 0x0F, 0x00, 0x00, 0x00,
};
```

`bMaxBurst = 0x0F` on EP4 tells the host it can batch up to 16 × 1024 B = 16 KB per burst, exactly matching the acquisition packet size. Set to `0x00` to revert to single-packet mode if the host has compatibility issues.

### 2. HSPI slave initialisation and ISR

```c
#include "CH56x_common.h"

#define PKT_SIZE    (8192u * 2u)   /* 16 KB per acquisition packet */

/* Ping-pong SRAM buffers; 4-byte aligned for DMA */
static __attribute__((aligned(4))) uint8_t hspi_buf[2][PKT_SIZE];
static volatile uint8_t hspi_fill_idx = 0;  /* buffer HSPI is writing into */
static volatile uint8_t pkt_ready     = 0;  /* set by ISR, cleared by main loop */
static volatile uint8_t pkt_ready_idx = 0;  /* which buffer is ready for USB3 TX */

void HSPI_Slave_Init(void) {
    /* Enable HSPI peripheral clock (SDK macro; may be SYS_ClockCmd or similar) */
    RCC_HSPI_ENABLE();

    /*
     * CFG: slave mode (RB_HSPI_MODE = 0), MSB first, DMA enabled.
     * CH569 HSPI default is SPI mode 0 (CPOL=0, CPHA=0).
     */
    R8_HSPI_CFG = RB_HSPI_MSB_FIRST | RB_HSPI_DMA_EN;

    /* Point DMA at buffer 0 for the first receive */
    R32_HSPI_RX_ADDR = (uint32_t)hspi_buf[0];
    R16_HSPI_DMA_LEN = PKT_SIZE;

    /* Clear pending flags, then enable RX-done and FIFO-overflow interrupts */
    R8_HSPI_INT_FLAG = RB_HSPI_IF_R_DONE | RB_HSPI_IF_FIFO_OV;
    R8_HSPI_INT_EN   = RB_HSPI_IE_R_DONE | RB_HSPI_IE_FIFO_OV;

    /* Enable HSPI in slave mode */
    R8_HSPI_CFG |= RB_HSPI_ENABLE;

    PFIC_EnableIRQ(HSPI_IRQn);
}

/*
 * HSPI ISR — fires when PKT_SIZE bytes have been received from RP2350B.
 * Swaps DMA to the alternate buffer (zero dead time) and signals the main loop.
 */
__attribute__((interrupt("WCH-Interrupt-fast")))
void HSPI_IRQHandler(void) {
    if (R8_HSPI_INT_FLAG & RB_HSPI_IF_FIFO_OV) {
        R8_HSPI_INT_FLAG = RB_HSPI_IF_FIFO_OV;
        /* FIFO overflow: RP2350B clocked too fast or ACK was not honoured */
    }

    if (R8_HSPI_INT_FLAG & RB_HSPI_IF_R_DONE) {
        R8_HSPI_INT_FLAG = RB_HSPI_IF_R_DONE;

        /* Record which buffer just filled, swap to the other */
        pkt_ready_idx       = hspi_fill_idx;
        hspi_fill_idx       = 1u - hspi_fill_idx;

        /* Re-arm DMA on the now-empty buffer */
        R32_HSPI_RX_ADDR = (uint32_t)hspi_buf[hspi_fill_idx];
        R16_HSPI_DMA_LEN = PKT_SIZE;

        /* Assert HSPI_ACK to release RP2350B for the next transfer */
        /* ACK is a GPIO toggled by firmware; exact mechanism is board-specific */
        GPIO_SetBits(HSPI_ACK_PORT, HSPI_ACK_PIN);

        pkt_ready = 1;
    }
}
```

### 3. USB3 bulk IN endpoint handler (EP4)

```c
/*
 * Send one 16 KB packet over USB3 EP4 bulk IN.
 *
 * The USB3 SS controller packetises automatically into 1024-byte bulk packets.
 * With bMaxBurst=15 on EP4, the host will accept all 16 packets in one burst.
 *
 * Register names follow WCH CH569 TRM (USBSS peripheral, endpoint 4).
 * Verify UEP4_TX_DMA / UEP4_TX_LEN / UEP4_TX_CTRL names against your EVT SDK.
 */
void USB3_EP4_BulkIN_Send(const uint8_t *buf, uint16_t len) {
    /* Spin until EP4 TX is not busy (previous transfer complete) */
    while (USBSS->UEP4_TX_CTRL & UEP_T_RES_BUSY);

    USBSS->UEP4_TX_DMA  = (uint32_t)buf;
    USBSS->UEP4_TX_LEN  = len;                          /* 16384 bytes */
    USBSS->UEP4_TX_CTRL = UEP_T_RES_ACK | UEP_T_AUTO_TOG;  /* arm TX */
}

/*
 * Main loop: drain the HSPI→USB3 pipeline.
 * Called from main() after USB3 enumeration completes and host opens EP4.
 */
void DataPipeline_Run(void) {
    while (1) {
        if (pkt_ready) {
            pkt_ready = 0;
            USB3_EP4_BulkIN_Send(hspi_buf[pkt_ready_idx], PKT_SIZE);
        }
    }
}
```

### 4. CDC-ACM endpoints (EP1 / EP2 / EP3)

CDC-ACM on a USB3 SS device is functionally identical to USB2 CDC-ACM — the class requests and data format are the same; only the endpoint descriptors and companion descriptors differ. The device must handle three EP0 class requests:

```c
typedef struct __attribute__((packed)) {
    uint32_t dwDTERate;    /* baud rate (e.g. 115200) */
    uint8_t  bCharFormat;  /* stop bits: 0=1, 1=1.5, 2=2 */
    uint8_t  bParityType;  /* 0=None, 1=Odd, 2=Even */
    uint8_t  bDataBits;    /* 5, 6, 7, 8, or 16 */
} CDC_LineCoding;

static CDC_LineCoding line_coding = { 115200, 0, 0, 8 };

/*
 * EP0 class request handler for Interface 0 (CDC communication).
 * Called from the USB3 stack's SETUP packet handler when bmRequestType
 * indicates class + interface and wIndex == 0.
 */
void CDC_ClassRequest_Handler(USB_SETUP_REQ *req, uint8_t **data_out, uint16_t *len_out) {
    switch (req->bRequest) {
    case CDC_SET_LINE_CODING:
        /* Host sends 7-byte line coding struct; copy on DATA stage */
        /* WCH stack calls this again with the data; update line_coding there */
        *len_out = 0;
        break;

    case CDC_GET_LINE_CODING:
        *data_out = (uint8_t *)&line_coding;
        *len_out  = sizeof(line_coding);
        break;

    case CDC_SET_CONTROL_LINE_STATE:
        /* wValue bit 0 = DTR, bit 1 = RTS; can gate EP4 TX on DTR if desired */
        *len_out = 0;
        break;

    default:
        /* Stall unknown class requests */
        USBSS->UEP0_TX_CTRL = UEP_T_RES_STALL;
        return;
    }
}

/*
 * CDC TX (device→host): write a string to EP2 bulk IN.
 * Use for debug output — identical in interface to a UART write.
 */
void CDC_SendString(const char *s) {
    uint16_t len = (uint16_t)strlen(s);
    while (USBSS->UEP2_TX_CTRL & UEP_T_RES_BUSY);
    memcpy(cdc_tx_buf, s, len);
    USBSS->UEP2_TX_DMA  = (uint32_t)cdc_tx_buf;
    USBSS->UEP2_TX_LEN  = len;
    USBSS->UEP2_TX_CTRL = UEP_T_RES_ACK | UEP_T_AUTO_TOG;
}
```

EP3 (interrupt IN, CDC notification) only needs to send a `SERIAL_STATE` notification when the control line state changes. For a data-only application, it can stay armed with length 0 and never fire.

### 5. Main initialisation outline

```c
int main(void) {
    /* System clock: configure for 120 MHz from 30 MHz crystal */
    SystemInit();          /* WCH SDK: sets PLL, flash wait states */

    /* Peripheral init */
    HSPI_Slave_Init();     /* HSPI slave DMA, ISR */
    USB3_DeviceInit();     /* WCH SDK: enumerate, register descriptor pointers */

    /* Register descriptors with the USB3 stack */
    USB3_SetDeviceDescriptor(USB3_DeviceDescriptor, sizeof(USB3_DeviceDescriptor));
    USB3_SetBOSDescriptor(USB3_BOSDescriptor, sizeof(USB3_BOSDescriptor));
    USB3_SetConfigDescriptor(USB3_ConfigDescriptor, sizeof(USB3_ConfigDescriptor));
    /* Register string descriptors (manufacturer, product) similarly */

    /* Wait for host to enumerate and open EP4 before starting pipeline */
    while (!USB3_IsConfigured());

    CDC_SendString("CH569 ready\r\n");

    /* Main data loop */
    DataPipeline_Run();    /* never returns */
}
```

## RP2350B Side (SPI Master + DMA)

### Design principles

- **SPI1 hardware peripheral** drives GPIO 10 (SCK) and GPIO 11 (MOSI). The hardware handles clock generation and bit shifting; Core 0 never spins in a byte loop.
- **DMA channel `dma_spi_tx`** is paced by `DREQ_SPI1_TX`. It reads from the acquisition ping-pong buffer and writes to the SPI1 TX FIFO. Core 0 programs the source address and triggers; the transfer runs autonomously.
- **Ping-pong buffer management**: two 16 KB buffers. While one is being clocked to CH569 via SPI DMA, the ADC capture DMA is filling the other. At 200 Hz PRF, each ADC capture takes ~5 ms and the 16 KB SPI transfer at 30 MHz takes ~4.3 ms — they overlap cleanly.
- **ACK handshake**: CH569 asserts GPIO 13 (HSPI_ACK) high once its HSPI DMA is re-armed and ready for the next 16 KB block. RP2350B polls this before asserting CS. Typical ACK latency: < 5 µs after previous CS deassert. A 2 ms timeout with CH569 reset guards against lock-up.
- **Core separation**: Core 0 owns ADC DMA, SPI DMA, and the ACK/CS GPIO logic. Core 1 is free for optional Hilbert processing via `multicore_fifo_push_blocking` (see `M33FPUHILBERT.md`). The DMA completion ISR and the ADC callback both run on Core 0.
- **No blocking in ISR**: the SPI DMA completion ISR only clears a flag and deasserts CS. The next transfer is started from the main loop or the ADC callback, never from inside an ISR, to avoid nested interrupt issues.

### Full implementation

```c
#include "pico/stdlib.h"
#include "hardware/spi.h"
#include "hardware/dma.h"
#include "hardware/gpio.h"
#include "hardware/irq.h"
#include "hardware/timer.h"

/* ── Pin assignments (SPI1 primary) ─────────────────────────── */
#define SPI_INST        spi1
#define SPI_SCK_PIN     10   /* SPI1_SCK — gpio_set_function(GPIO_FUNC_SPI) */
#define SPI_MOSI_PIN    11   /* SPI1_TX  — gpio_set_function(GPIO_FUNC_SPI) */
#define SPI_CS_PIN      12   /* manual GPIO out — held low for entire 16 KB burst */
#define HSPI_ACK_PIN    13   /* GPIO in  — CH569 asserts high when HSPI DMA re-armed */
#define CH569_RST_PIN   14   /* GPIO out — active-low, < 10 ms pulse to reset CH569 */

/* ── Transfer parameters ─────────────────────────────────────── */
#define SPI_CLK_HZ      30000000u   /* 30 MHz; after validation raise to 60 MHz */
#define PKT_SIZE        (8192u * 2u) /* 16 KB — 8192 samples × 2 bytes (uint16) */
#define ACK_TIMEOUT_US  2000u        /* 2 ms: max wait for CH569 ACK before reset */

/* ── Ping-pong acquisition buffers ──────────────────────────── */
static uint8_t ch569_buf[2][PKT_SIZE] __attribute__((aligned(4)));
static volatile uint8_t buf_fill_idx = 0;   /* buffer ADC DMA is writing into */
static volatile uint8_t buf_send_idx = 0;   /* buffer queued for next SPI DMA */
static volatile bool    spi_dma_busy = false;
static volatile bool    pkt_pending  = false; /* ADC done while SPI still busy */

/* ── DMA channel handle ──────────────────────────────────────── */
static int dma_spi_tx;

/* ── Forward declarations ────────────────────────────────────── */
static void spi_dma_done_irq(void);
static void start_spi_dma(uint8_t buf_idx);
static void ch569_reset(void);

/* ================================================================
 * ch569_init — call once during system startup, before main loop
 * ================================================================ */
void ch569_init(void) {
    /* Hold CH569 in reset briefly, then release */
    gpio_init(CH569_RST_PIN);
    gpio_set_dir(CH569_RST_PIN, GPIO_OUT);
    ch569_reset();

    /* ACK input with pull-down: default state is "not ready" */
    gpio_init(HSPI_ACK_PIN);
    gpio_set_dir(HSPI_ACK_PIN, GPIO_IN);
    gpio_pull_down(HSPI_ACK_PIN);

    /* Manual CS: deasserted high at startup */
    gpio_init(SPI_CS_PIN);
    gpio_set_dir(SPI_CS_PIN, GPIO_OUT);
    gpio_put(SPI_CS_PIN, 1);

    /* SPI1: SCK + MOSI only (no MISO — TX-only path to CH569) */
    spi_init(SPI_INST, SPI_CLK_HZ);
    spi_set_format(SPI_INST, 8, SPI_CPOL_0, SPI_CPHA_0, SPI_MSB_FIRST);
    gpio_set_function(SPI_SCK_PIN,  GPIO_FUNC_SPI);
    gpio_set_function(SPI_MOSI_PIN, GPIO_FUNC_SPI);

    /* DMA channel: ch569_buf[n] → SPI1 TX FIFO, paced by DREQ_SPI1_TX */
    dma_spi_tx = dma_claim_unused_channel(true);
    dma_channel_config cfg = dma_channel_get_default_config(dma_spi_tx);
    channel_config_set_transfer_data_size(&cfg, DMA_SIZE_8);
    channel_config_set_dreq(&cfg, DREQ_SPI1_TX);
    channel_config_set_read_increment(&cfg, true);   /* advance through source buffer */
    channel_config_set_write_increment(&cfg, false); /* fixed dest: SPI1 DR */
    dma_channel_configure(
        dma_spi_tx, &cfg,
        &spi_get_hw(SPI_INST)->dr,  /* destination: SPI1 data register (TX FIFO) */
        NULL,                        /* source: set per-transfer in start_spi_dma() */
        PKT_SIZE,                    /* 16384 bytes per transfer */
        false                        /* do not start yet */
    );

    /* Enable DMA_IRQ_0 for the SPI TX channel */
    dma_channel_set_irq0_enabled(dma_spi_tx, true);
    irq_set_exclusive_handler(DMA_IRQ_0, spi_dma_done_irq);
    irq_set_enabled(DMA_IRQ_0, true);
}

/* ================================================================
 * DMA completion ISR — runs on Core 0
 *
 * The SPI DMA fires when all PKT_SIZE bytes have been written to the
 * SPI1 TX FIFO. The SPI shift register may still be draining — wait
 * for it before deasserting CS so CH569 sees a clean burst boundary.
 * ================================================================ */
static void spi_dma_done_irq(void) {
    dma_hw->ints0 = 1u << dma_spi_tx;     /* clear the interrupt flag */

    /* Drain the SPI shift register — last byte still in flight */
    while (spi_get_hw(SPI_INST)->sr & SPI_SSPSR_BSY_BITS);

    gpio_put(SPI_CS_PIN, 1);               /* deassert CS; CH569 HSPI ISR fires */
    spi_dma_busy = false;

    /* If an ADC packet arrived while we were busy, start it now */
    if (pkt_pending) {
        pkt_pending = false;
        start_spi_dma(buf_send_idx);
    }
}

/* ================================================================
 * start_spi_dma — assert CS, wait for ACK, launch DMA
 *
 * Must NOT be called from the SPI DMA ISR directly (would nest).
 * Call from: ADC completion callback (when spi_dma_busy == false),
 *            SPI DMA ISR via the pkt_pending flag,
 *            or ch569_poll() in the main loop.
 * ================================================================ */
static void start_spi_dma(uint8_t buf_idx) {
    /* Wait for CH569 HSPI_ACK high — its DMA is re-armed and ready */
    uint32_t t0 = time_us_32();
    while (!gpio_get(HSPI_ACK_PIN)) {
        if ((time_us_32() - t0) > ACK_TIMEOUT_US) {
            ch569_reset();              /* CH569 locked up — hard reset */
            return;
        }
    }

    spi_dma_busy = true;
    gpio_put(SPI_CS_PIN, 0);           /* assert CS: signals start of 16 KB burst */

    /* Reconfigure DMA source and trigger */
    dma_channel_set_read_addr(dma_spi_tx, ch569_buf[buf_idx], true /* start */);
}

/* ================================================================
 * ch569_adc_done_cb — called by ADC DMA completion handler
 *
 * `filled_idx` is the buffer just completed by ADC DMA.
 * The ADC subsystem must re-arm its own DMA on buf_fill_idx
 * (the alternate buffer) BEFORE calling this.
 * ================================================================ */
void ch569_adc_done_cb(uint8_t filled_idx) {
    buf_send_idx = filled_idx;
    buf_fill_idx = 1u - filled_idx;    /* ADC subsystem fills the other buffer next */

    if (!spi_dma_busy) {
        start_spi_dma(buf_send_idx);
    } else {
        /* SPI transfer of previous packet still running.
         * At 30 MHz / 16 KB = 4.3 ms transfer and 5 ms inter-pulse gap (200 Hz),
         * this overlap should not occur — but flag it defensively. */
        pkt_pending = true;
    }
}

/* ================================================================
 * ch569_poll — call from Core 0 main loop
 *
 * Catches the race where ADC completed while SPI was busy AND the
 * SPI ISR already cleared spi_dma_busy before pkt_pending was set.
 * In practice rare, but safe to call every loop iteration.
 * ================================================================ */
void ch569_poll(void) {
    if (!spi_dma_busy && pkt_pending) {
        pkt_pending = false;
        start_spi_dma(buf_send_idx);
    }
}

/* ================================================================
 * ch569_reset — 10 ms active-low pulse on RESET# pin
 * ================================================================ */
static void ch569_reset(void) {
    gpio_put(CH569_RST_PIN, 0);
    sleep_ms(10);
    gpio_put(CH569_RST_PIN, 1);
    sleep_ms(100);    /* allow CH569 to re-enumerate over USB3 */
}
```

### Ping-pong timing at 200 Hz PRF

```
Time →   0 ms          4.3 ms    5 ms        9.3 ms   10 ms
          │              │         │            │        │
ADC buf A: [══ capture ══]         [═══ capture (A again) ════]
SPI DMA:                [══ A→CH569 ══]        [══ B→CH569 ══]
ADC buf B:    [═══════════ capture ═══════════]
              │                   │
          buf_fill=1           buf_fill=0
          buf_send=0           buf_send=1
```

The SPI transfer (4.3 ms at 30 MHz) fits inside the 5 ms inter-pulse gap. Core 0 is free for the remaining 0.7 ms per cycle, and Core 1 is completely unblocked throughout.

## CH569 vs FT2232H — Detailed Comparison

The brief decision table at the top covers when to choose each. This section goes deeper on each axis for the ultr4rick use case.

### Throughput ceiling

FT2232H in sync 245 FIFO mode is clock-mastered by the FTDI chip at 60 MHz CLKOUT. The 8-bit parallel data path gives 60 MB/s theoretical; USB 2.0 HS protocol overhead (~17%) brings practical sustained throughput to ~40 MB/s. The ceiling is hard — no firmware tuning changes it.

CH569 presents two ceilings: the USB3 SS bulk pipe (~350–400 MB/s), and the RP2350B→CH569 serial SPI link (7.5 MB/s at 60 MHz, 9.375 MB/s at 75 MHz). FT2232H's 8-bit parallel FIFO at ~40 MB/s significantly exceeds CH569's serial SPI ceiling. For the ultrasound use cases at 200–400 Hz PRF (3.2–6.5 MB/s), both fit within CH569's serial ceiling, but FT2232H has far more headroom. The CH569 advantages are the USB3 SS endpoint (much faster USB hop once data is in CH569 SRAM), true CDC-ACM composite, and zero-install Linux — not raw throughput through the RP2350B→CH569 coupling.

### Clock mastering direction

This is a subtle but important difference in firmware complexity:

- **FT2232H**: FTDI drives CLKOUT at 60 MHz; RP2350B must synchronise its writes to this external clock. PIO is required (hardware SPI ignores external clocks). See `FT2232H.md` for the PIO state machine that monitors TXE# and CLKOUT.
- **CH569**: RP2350B is SPI master; it drives the clock. Hardware SPI1 with DMA is sufficient — no PIO required, no external clock synchronisation. Simpler firmware on the RP2350B side.

### Host driver complexity

| | FT2232H | CH569 |
|--|---------|-------|
| **Linux** | Must unload `ftdi_sio` kernel module (or add udev `ATTR{idVendor}` rule) before libftdi can claim the device. libftdi installed separately (`apt install libftdi1-dev`). | `cdc_acm` claims Interface 0–1 automatically; Interface 2 left free for libusb. Zero config: `pip install pyusb` + `usb.core.find()`. |
| **Windows** | Zadig must replace the FTDI VCP driver with WinUSB or libusbK before libftdi works. FTDI's D2XX has a proprietary installer (FTDIChipCDM.exe). Either path requires an admin install step. | CDC-ACM appears as a COM port automatically (built-in `usbser.sys`, Windows 10+). Vendor bulk EP needs WinUSB — can be automated via MS OS 2.0 Descriptor embedded in CH569 firmware (no Zadig for end user). |
| **macOS** | libftdi available via Homebrew; Apple's ftdi_sio equivalent must be unloaded (`sudo kextunload -b com.apple.driver.AppleUSBFTDI`). | Standard USB CDC + libusb; no kernel extension conflict. |

CH569 is strictly better on Linux (zero-install) and roughly equivalent on Windows (both need a one-time driver assignment for the bulk endpoint, but CH569 can self-configure via MS OS Descriptor).

### Composite device support

FT2232H has two independent channels (A and B). Channel A handles high-speed FIFO data; Channel B can be configured as UART in EEPROM. They appear to the host as two separate USB devices (two VID/PID entries) in the default multi-interface configuration, or as one device with two interfaces depending on EEPROM settings. The CDC-ACM serial port is not natively CDC-ACM — it uses the FTDI VCP protocol, which requires the FTDI driver. It is not a standard `ttyACM` device.

CH569 presents a true IAD composite: Interface 0–1 are standard CDC-ACM (opens as `/dev/ttyACM0` on Linux, `COMx` on Windows, `tty.usbmodem*` on macOS — no FTDI driver). Interface 2 is vendor bulk. One USB descriptor, one cable, one device to manage.

### Latency for 16 KB packet delivery

Transfer time = packet_size / throughput:
- FT2232H: 16 384 / (40 × 10⁶) ≈ **0.41 ms** + USB HS scheduling overhead (~125 µs micro-frame)
- CH569 (SPI @ 60 MHz + USB3 SS): SPI transfer 16 384 / (60 × 10⁶) ≈ 2.7 ms; USB3 transfer 16 384 / (350 × 10⁶) ≈ **0.047 ms**; total pipeline ≈ 2.75 ms

CH569's USB3 hop is 8× faster than FT2232H's USB2 hop, but the SPI link to load the CH569 SRAM takes 2.7 ms — longer than the FT2232H approach end-to-end. For latency, FT2232H (0.41 ms USB transfer after data is ready) actually wins over CH569 (2.7 ms SPI load + 0.047 ms USB transfer) at 60 MHz SPI. Only at > 120 MHz SPI equivalent would CH569 win on total pipeline latency.

**Conclusion for latency:** if data is already in RP2350B SRAM and the goal is to get it to the host as fast as possible, FT2232H delivers it faster because it avoids the RP2350B→CH569 SPI hop. CH569's latency advantage is in the USB3 segment only.

### Power

| | FT2232H | CH569 |
|--|---------|-------|
| Core | FTDI ASIC at 3.3V; no MCU overhead | RISC-V core at 120 MHz, 3.3V |
| USB PHY | USB 2.0 HS PHY | USB 3.0 SS PHY (significantly more complex) |
| Estimated active current | 60–150 mA @ 3.3V (0.2–0.5 W) | 120–200 mA @ 3.3V (0.4–0.66 W) |
| Notes | FT2232H has a low-power PWRSAV# mode | CH569 USB3 PHY has no low-power equivalent during active streaming |

FT2232H uses less power. For battery-operated ultr4rick the difference (up to ~0.2 W) is meaningful.

### Cost

- FT2232H IC (bare LQFP-48): ~€5. Mini-module: ~€12–18.
- CH569W (bare LQFP-64): ~€2–4 from LCSC. No module available.

CH569 is cheaper on BOM, but the firmware development cost is significant.

### Ecosystem maturity

FT2232H has been in production since ~2008. There are thousands of examples, bindings in every language (Python, Rust, Julia, MATLAB, LabVIEW), and deep integration with test tools (OpenOCD, pyOCD, sigrok). The synchronous FIFO mode is well-documented with known errata.

CH569 was released around 2022. WCH's documentation is mostly in Chinese (though EVT examples have English comments). The USB3 + HSPI combination is niche — few open-source examples exist outside WCH's own EVT package. MounRiver Studio is functional but the Eclipse base shows its age. The WCH RISC-V toolchain does not interoperate with standard LLVM.

### Firmware development burden

| | RP2350B side | Bridge side | Host side |
|--|-------------|-------------|-----------|
| **FT2232H** | PIO state machine (100 LoC) | None — FT_Prog EEPROM config | libftdi Python (10 LoC) |
| **CH569** | SPI DMA init + ISR (~150 LoC) | Full RISC-V USB3 firmware (~500 LoC) | pyusb Python (15 LoC) |

### Decision summary

| Want | Choose |
|------|--------|
| Minimum firmware complexity, proven ecosystem | FT2232H |
| Single USB-C cable with zero-install Linux CDC | CH569 |
| > 9 MB/s throughput (RP2350B→bridge) | FT2232H (parallel FIFO, ~40 MB/s) |
| Lowest power | FT2232H |
| Lowest BOM cost (bare IC) | CH569 |
| Latency-critical (< 1 ms total to host) | FT2232H |
| USB3 SS endpoint for fastest host-side delivery | CH569 |

## Maximising USB3 Throughput with CH569

The USB3 SS pipe can sustain ~350–400 MB/s. The RP2350B→CH569 SPI link is the ceiling at ~60–75 MB/s. This section covers every practical lever to raise that ceiling and to exploit USB3's bandwidth as fully as possible.

### 1. Raise SPI clock: 30 → 75 MHz

At 150 MHz RP2350B system clock, SPI1 hardware maximum is system_clock / 2 = **75 MHz**:

```c
/* In ch569_init(): replace SPI_CLK_HZ with the target */
spi_init(SPI_INST, 75000000u);  /* 75 MHz — verify CH569 HSPI slave max from TRM */
```

The Pico SDK rounds to the nearest achievable rate: `actual = 150 MHz / round(150 / (2 × 75))` = 75 MHz exactly. At 75 MHz serial SPI: **9.375 MB/s**, 16 KB transfer in **1.75 ms** (vs 4.37 ms at 30 MHz; vs 2.18 ms at 60 MHz).

Validation procedure: start at 30 MHz, increment by 5 MHz per test, check for HSPI FIFO overflow interrupt (`RB_HSPI_IF_FIFO_OV`) on CH569 side, and for corrupted data (CRC or sequence counter check). The CH569 HSPI slave maximum clock is specified in the TRM — likely 60–80 MHz. Do not assume 75 MHz works without this check.

**Result at 75 MHz: serial SPI throughput rises from 3.75 MB/s (30 MHz) to 9.375 MB/s. This is adequate for ≤ 400 Hz PRF pulsed ultrasound (6.5 MB/s). Continuous 65 Msps streaming (~130 MB/s) is not achievable via serial SPI regardless of clock rate.**

### 2. PIO-based SPI or parallel output

For the serial HSPI path, hardware SPI + DMA is preferred over PIO — same 75 MHz ceiling, less code. PIO is the fallback for non-power-of-2 clock ratios (e.g., exactly 60 MHz) or per-byte flow-control granularity.

**For a genuine throughput increase:** CH569 HSPI does support parallel modes (`RB_HSPI_DAT8_MOD` / `RB_HSPI_DAT16_MOD` / `RB_HSPI_DAT32_MOD` in `R8_HSPI_CFG`). In 8-bit mode, a PIO state machine uses `out pins, 8` to output one byte per clock cycle — 13 GPIO total (HD0–HD7 + clock + 4 handshake signals), up to ~50–60 MB/s sustained. See [CH569 HSPI — Parallel Bus Mode](#ch569-hspi--parallel-bus-mode) for the full signal interface and reference implementations.

### 3. bMaxBurst and MaxPacketSize — already at spec maximum

The EP4 SS Endpoint Companion Descriptor already has:
- `wMaxPacketSize = 1024` — SS bulk maximum per USB 3.0 spec
- `bMaxBurst = 0x0F` — 16 packets × 1024 B = 16 KB per burst sequence

These cannot be increased further under USB 3.0. The host schedules 16 consecutive bulk packets without re-arbitrating the bus, delivering the full 16 KB in ~0.047 ms at 350 MB/s. No descriptor tuning remains.

For USB 3.1 Gen 2 (10 Gbps), `bmAttributes` in the SS companion descriptor could encode multi-stream, but CH569 is USB 3.0 only.

### 4. Host-side async URB queuing

The synchronous host pattern (read 16 KB → process → read 16 KB) leaves the USB3 pipe idle during Python execution. The xhci host controller can pipeline multiple outstanding URBs — but only if they are submitted before the previous one completes.

**Synchronous (suboptimal):**
```python
while True:
    data = dev.read(0x84, 16384, timeout=1000)   # blocks until 16 KB arrives
    process(data)                                  # USB pipe idle here
```

**Async with `usb1` (better):**
```python
import usb1, threading, queue

PKT = 16384
QUEUE_DEPTH = 4   # 4 URBs outstanding; fills USB3 pipeline

rx_queue = queue.Queue()

def callback(transfer):
    if transfer.getStatus() == usb1.TRANSFER_COMPLETED:
        rx_queue.put(bytes(transfer.getBuffer()[:transfer.getActualLength()]))
    transfer.submit()   # re-submit immediately

with usb1.USBContext() as ctx:
    dev = ctx.openByVendorIDAndProductID(0x1A86, 0x5569)
    dev.claimInterface(2)

    transfers = []
    for _ in range(QUEUE_DEPTH):
        t = dev.getTransfer()
        t.setBulk(0x84, PKT, callback)
        t.submit()
        transfers.append(t)

    # Process packets from the queue while USB runs in background
    while True:
        data = rx_queue.get()
        process(data)
```

With 4 URBs queued, the xhci driver keeps the USB3 pipe busy across packet boundaries. Practical throughput improvement: 20–40% in Python hosts; less significant in C (libusb async API gives similar pipelining).

### 5. Zero-copy DMA on CH569 side (already implemented)

The design already routes HSPI DMA directly into the SRAM ping-pong buffer and launches USB3 DMA from the same buffer address — no `memcpy`. This is the correct zero-copy architecture. No further optimisation is possible in the SRAM→USB3 path.

The only remaining internal CH569 latency is the HSPI ISR execution time (< 1 µs) to swap buffer pointers and arm the USB3 DMA.

### 6. CH569 SerDes interface (alternative high-speed path)

CH569 has a SerDes block documented in the TRM. If it exposes external pins (distinct from the USB3 PIPE PHY), this could replace the HSPI link:

- **CH569 SerDes RX**: differential serial input, potentially up to ~480 Mbit/s
- **RP2350B HSTX output**: 8-bit parallel at up to 150 Mbit/s per bit; or 1 bit at 300 Mbit/s on a single GPIO via HSTX serialiser mode
- **Mismatch**: HSTX is 3.3V CMOS single-ended; SerDes expects LVDS (100 Ω differential, ~350 mV swing). A level translator IC (e.g., SN65LVDS1) bridges this.
- **Effective link**: 300 Mbit/s serial → 37.5 MB/s, worse than HSPI at 60 MHz (60 MB/s)

Unless CH569's SerDes supports multi-lane operation (which the TRM would need to confirm), this path offers no throughput advantage over HSPI and adds hardware complexity. Verify against CH569 TRM §SerDes before pursuing.

### 7. Architectural ceiling and alternatives

If the target throughput is truly > 100 MB/s sustained (e.g., full 65 Msps uncompressed at 400+ Hz PRF = 130 MB/s), neither FT2232H nor the CH569+SPI combination reaches it. Options:

| Architecture | RP2350B interface | RP2350B→bridge ceiling | Complexity |
|-------------|-----------------|----------------------|------------|
| FT2232H (current FT2232H.md) | PIO 245 FIFO (8-bit parallel) | ~40 MB/s | Low |
| CH569 + SPI1 @ 75 MHz (serial HSPI) | Hardware SPI1 DMA | ~9.375 MB/s | Medium |
| CH569 + PIO 8-bit parallel HSPI | PIO 8× data GPIO + 5 handshake | **~50–60 MB/s** | High |
| CH569 + PIO 16-bit parallel HSPI | PIO 16× data GPIO + 5 handshake (21 total) | **~100–120 MB/s** | High (PCB harder; PIO code unchanged) |
| CH569 HSPI 32-bit via FPGA | FPGA parallel bus | **~154 MB/s** (demonstrated) | FPGA required |
| Cypress FX3 + GPIF II (32-bit parallel @ 100 MHz) | RP2350B PIO 8-pin parallel | ~320 MB/s | High |
| FPGA (Gowin GW2A + USB3 PIPE PHY) | Parallel LVDS | > 400 MB/s | Very high |

For ultr4rick at 200–400 Hz PRF with 8192 samples/acquisition (~3.3–6.6 MB/s), both FT2232H and CH569 serial SPI are sufficient. FT2232H has more headroom and less firmware. CH569 is warranted for the USB3 SS endpoint + CDC-ACM composite in a single connector. The Cypress FX3 or FPGA path is warranted only for continuous full-rate uncompressed streaming (> 40 MB/s), which is a different product class.

## CH569 HSPI — Parallel Bus Mode

CH569 HSPI is not a serial SPI variant — it is a genuine **high-speed parallel bus** with a configurable 8/16/32-bit data width, hardware DMA, CRC, and a request/acknowledge handshake protocol. The serial use described above is a reduced operating mode. The full parallel bus is what enables the ~150+ MB/s link rates demonstrated in open-source implementations.

### Reference implementations

**[amaranth-farm/ch569-hspi-fpga](https://github.com/amaranth-farm/ch569-hspi-fpga)** — Amaranth HDL gateware implementing both HSPI transmitter and receiver cores for a Colorlight ECP5 FPGA board. Provides a clean stream interface on the FPGA side with CRC validation, loopback testing, and an ILA (Integrated Logic Analyser) for protocol debugging. Demonstrates CH569 ↔ FPGA communication over the full 32-bit HSPI bus. The `HSPIInterface` record defines all bus signals:

```python
LAYOUT = [
    ('hd', [('i', 32, DIR_FANIN), ('o', 32, DIR_FANOUT), ('oe', 1, DIR_FANOUT)]),
    ("tx_ack",    1, DIR_FANOUT),   # HTRDY: slave ready
    ("tx_ready",  1, DIR_FANIN),    # HTACK: master ready acknowledge
    ("tx_req",    1, DIR_FANOUT),   # HRACT: transmit request
    ("rx_act",    1, DIR_FANIN),    # HTREQ: receive active
    ("tx_valid",  1, DIR_FANOUT),   # HRVLD: data valid (TX)
    ("rx_valid",  1, DIR_FANIN),    # HTVLD: data valid (RX)
]
```

Plus separate TX clock (HRCLK) and RX clock (HTCLK) lines.

**[hydrausb3/hydrausb3_fw — HydraUSB3_DualBoard_HSPI](https://github.com/hydrausb3/hydrausb3_fw/tree/main/HydraUSB3_DualBoard_HSPI)** — CH569 C firmware for two HydraUSB3 v1 boards wired together via HSPI. One board runs as HSPI host (TX), the other as device (RX). The example transfers 32 KB at 120 MHz system clock in 32-bit mode:

```c
#define FREQ_SYS   (120000000)          /* CH569 system clock = HSPI clock */
#define Data_Size  DataSize_32bit       /* RB_HSPI_DAT32_MOD */
#define DMA_Tx_Len (512)                /* 512 words × 4 bytes = 2 KB per DMA chunk */

HSPI_DoubleDMA_Init(HSPI_HOST, RB_HSPI_DAT32_MOD, TX_DMA_Addr0, TX_DMA_Addr1, DMA_Tx_Len);
HSPI_DMA_Tx();  /* sends 32 KB using dual-DMA ping-pong */
```

**Measured timing from serial log:**
```
00s 001ms 166us  Start Tx 32K data
00s 001ms 378us  Tx 32K data suc
```
**Transfer time: 212 µs for 32 768 bytes = ~154 MB/s actual throughput** (at 120 MHz system clock, with some UART log overhead; raw DMA-only rate approaches theoretical maximum).

### Data width modes and throughput

| Mode | Data pins | Clock | Theoretical | Demonstrated |
|------|-----------|-------|------------|--------------|
| 8-bit (`RB_HSPI_DAT8_MOD`) | HD0–HD7 | 120 MHz | 120 MB/s | — |
| 16-bit (`RB_HSPI_DAT16_MOD`) | HD0–HD15 | 120 MHz | 240 MB/s | — |
| 32-bit (`RB_HSPI_DAT32_MOD`) | HD0–HD31 | 120 MHz | 480 MB/s | **~154 MB/s** |

### Frame structure

Every HSPI transfer is framed with a 32-bit header and a 32-bit Ethernet CRC (polynomial 0x04C11DB7), both handled in hardware/DMA:

```
[ 32-bit header (UDF0: 26-bit user ID + 4-bit sequence + 2-bit TLL) ]
[ payload: up to 4096 × 32-bit words = 16 KB max per frame ]
[ 32-bit CRC ]
```

Maximum payload per frame: **16 KB** (matches one acquisition packet). Header + CRC overhead: 8 bytes on 16 384 bytes = 0.05%.

### Signal interface (CH569 side)

| Signal | CH569 role | Direction (HSPI host TX mode) |
|--------|-----------|-------------------------------|
| HD0–HD7 (8-bit) or HD0–HD31 (32-bit) | Parallel data bus | CH569→slave |
| HRCLK | TX clock output | CH569→slave |
| HTCLK | RX clock input | slave→CH569 |
| HRACT / `tx_req` | Transmit request | CH569→slave |
| HTACK / `tx_ready` | Slave ready acknowledge | slave→CH569 |
| HTRDY / `tx_ack` | Slave DMA re-armed | slave→CH569 |
| HRVLD / `tx_valid` | Data valid | CH569→slave |

In slave (device) mode — the role when receiving from RP2350B — direction reverses: RP2350B drives clock and data, CH569 asserts HTRDY when its DMA is re-armed.

### RP2350B feasibility — 8-bit HSPI via PIO

RP2350B has no native parallel bus output. The only path is PIO:

**8-bit mode (practical):**

| Signal group | GPIO count | RP2350B implementation |
|-------------|-----------|----------------------|
| HD0–HD7 (data) | 8 | PIO `out pins, 8` |
| HRCLK (clock) | 1 | PIO sideset or dedicated SM |
| HRACT / tx_req | 1 | PIO GPIO or ARM |
| HTACK / tx_ready | 1 | PIO `wait gpio` |
| HTRDY / tx_ack | 1 | PIO or ARM interrupt |
| HRVLD / tx_valid | 1 | PIO sideset |
| **Total** | **13** | **vs 5 for serial path** |

PIO at 150 MHz system clock with a 2-instruction output loop (set data → toggle clock): **75 MHz byte rate = 75 MB/s theoretical**. With handshake protocol overhead: **~50–60 MB/s sustained** — 5–6× the serial SPI ceiling.

Dual DMA on RP2350B feeds the PIO TX FIFO; a second PIO state machine (or ARM GPIO ISR) monitors HTACK/HTRDY for flow control. The handshake FSM (assert HRACT → wait HTACK → drive HD + HRVLD) maps to ~10 PIO instructions.

**16-bit mode:** Feasible on RP2350B (not RP2350A) — 16 data + 5 control = 21 GPIOs, within RP2350B's 48-GPIO bank. See section below. **32-bit mode** requires an FPGA: 32 data pins + 5 control = 37 GPIOs, which exceeds a single PIO output window.

### RP2350B 16-bit HSPI via PIO — Implementation Details

#### Why 16-bit is feasible on RP2350B but not RP2350A

RP2350A has 30 GPIOs (GPIO0–GPIO29). After allocating 13 pins for 8-bit HSPI, only 17 remain for the rest of the board (SPI to ADC, HV triggers, mux control). Adding 8 more data lines leaves 9 — not workable.

RP2350B has 48 GPIOs (GPIO0–GPIO47) in its QFN-80 package. Critically, the QSPI flash interface uses **dedicated physical pads** (QSPI_SS, QSPI_SCLK, QSPI_SD0–SD3) that are **separate from the GPIO numbering** — they are not GPIO30–GPIO47 in disguise. All 48 GPIO-numbered pins are free for general use. 16-bit HSPI occupies GPIO0–GPIO20 (21 pins), leaving GPIO21–GPIO47 (27 pins) for the rest of the design.

#### GPIO pin assignment

| GPIO | Signal | Direction (RP2350B) | Notes |
|------|--------|---------------------|-------|
| GPIO0–GPIO15 | HDAT[15:0] | OUT | 16-bit data bus — consecutive block for `out pins, 16` |
| GPIO16 | HTCLK | OUT | PIO sideset — clock to CH569 |
| GPIO17 | HRACT | OUT | PIO sideset or ARM GPIO — transfer-active assertion |
| GPIO18 | HRVLD | OUT | PIO sideset — data-valid strobe |
| GPIO19 | HTACK | IN | CH569 → RP2350B acknowledge; PIO `wait gpio 19` |
| GPIO20 | HTRDY | IN | CH569 → RP2350B DMA re-armed; PIO `wait gpio 20` |
| **Total** | | | **21 GPIOs** |

GPIO0–GPIO20 all fall within `GPIOBASE = 0` (PIO GPIO window: GPIO0–GPIO31). No bank switching required. PIO2 (new on RP2350; not present on RP2040) can be dedicated to HSPI, leaving PIO0 and PIO1 for the rest of the design.

#### PIO program — SM0 (data output)

```pio
; 16-bit HSPI TX state machine
; Sideset 2 bits: bit[1] = HTCLK, bit[0] = HRVLD
; Out pins: GPIO0–GPIO15 (HDAT[15:0])
; System clock: 150 MHz → loop = 2 cycles → 75 MHz clock rate

.program hspi_tx_16
.side_set 2

.wrap_target
    out pins, 16   side 0b10   ; output 16 data bits; HTCLK low, HRVLD high (data setup)
    nop            side 0b11   ; HTCLK rising edge — CH569 latches HDAT on this edge
.wrap
```

- PIO FIFO is 32-bit wide. With `autopull` threshold = 32, each 32-bit FIFO entry yields **two** 16-bit output cycles (OSR shifts twice before autopull). DMA transfers 32-bit words.
- `out pins, 16` costs **1 PIO cycle** — identical to `out pins, 8`. The 8-bit and 16-bit programs differ only in the immediate operand; loop structure, sideset, and DMA config are the same.
- Theoretical throughput: 75 MHz × 16 bits / 8 = **150 MB/s**. Sustained with handshake overhead: **~100–120 MB/s**.

#### PIO program — SM1 (handshake control)

```pio
; HSPI handshake state machine
; Set pin: GPIO17 (HRACT)
; Waits: GPIO20 (HTRDY), GPIO19 (HTACK)

.program hspi_handshake
    set pins, 1        ; assert HRACT — signal to CH569 that a frame is coming
    wait 1 gpio 20     ; wait for CH569 HTRDY — slave DMA buffer is armed
    wait 1 gpio 19     ; wait for CH569 HTACK — frame start acknowledged
    set pins, 0        ; deassert HRACT
    irq set 0          ; signal ARM: handshake done, DMA may start SM0
```

ARM firmware triggers SM1 before each frame. SM1 completes handshake and fires IRQ. ARM then arms DMA → SM0 runs autonomously until the TX FIFO empties. CH569's hardware CRC (Ethernet polynomial 0x04C11DB7) runs in parallel on the CH569 side; the RP2350B does not compute CRC.

#### DMA chaining

```c
// Channel 0: pump acquisition buffer into PIO0 SM0 TX FIFO
dma_channel_config c0 = dma_channel_get_default_config(ch0);
channel_config_set_transfer_data_size(&c0, DMA_SIZE_32);   // 32-bit words (2× 16-bit output per word)
channel_config_set_dreq(&c0, DREQ_PIO0_TX0);               // pace to SM0 TX FIFO level
channel_config_set_chain_to(&c0, ch1);                     // chain to reload channel for ping-pong
channel_config_set_read_increment(&c0, true);
channel_config_set_write_increment(&c0, false);
dma_channel_configure(ch0, &c0,
    &pio0->txf[0],   // destination: PIO0 SM0 TX FIFO
    acq_buf,         // source: ADC acquisition buffer in SRAM
    acq_words,       // word count = frame_bytes / 4
    false);

// Channel 1: reload ch0 read address for next frame (optional ping-pong)
```

RP2350B has 12 DMA channels and supports `chain_to` for automatic reload — no IRQ latency between back-to-back frames.

#### RP2350B GPIO allocation for ultr4rick

| GPIO range | Use |
|-----------|-----|
| GPIO0–GPIO20 | 16-bit HSPI to CH569 (21 pins — this section) |
| GPIO21–GPIO25 | SPI0 to ADC: MOSI, MISO, CLK, CS0, CS1 |
| GPIO26–GPIO29 | Analog mux: HC4051 A0/A1/A2/EN |
| GPIO30–GPIO35 | HV trigger, HV gate, T/R switch, blanking gate |
| GPIO36–GPIO47 | I²C, UART debug, LED, IMU SPI, spare |

On RP2350A (30 GPIOs), 16-bit HSPI alone consumes GPIO0–GPIO20, leaving only GPIO21–GPIO29 (9 pins) for the entire rest of the design. RP2350B is a **hard requirement** for 16-bit PIO HSPI.

#### 16-bit vs 8-bit — what actually differs

| Dimension | 8-bit HSPI via PIO | 16-bit HSPI via PIO |
|-----------|-------------------|---------------------|
| PIO `out` instruction | `out pins, 8` | `out pins, 16` |
| PIO cycles per word | 1 | 1 — identical cost |
| GPIO pins total | 13 | 21 |
| Throughput (sustained) | ~50–60 MB/s | ~100–120 MB/s |
| PCB | 8 length-matched traces | 16 length-matched traces; simultaneous switching noise (SSN) from 16 transitions at 75 MHz |
| Firmware structure | — | Identical |
| MCU requirement | RP2350A or RP2350B | **RP2350B only** |

### Throughput comparison: serial SPI vs parallel HSPI vs FPGA

| RP2350B→CH569 path | Throughput | GPIO pins | Key constraint |
|-------------------|-----------|-----------|----------------|
| Serial SPI (hardware SPI1 + DMA) | 9.375 MB/s | 5 | — |
| 8-bit HSPI via PIO | ~50–60 MB/s | 13 | PIO handshake FSM |
| **16-bit HSPI via PIO** | **~100–120 MB/s** | **21** | PCB: 16 length-matched traces; SSN from 16 simultaneous transitions at 75 MHz. PIO code unchanged (`out pins, 16` costs 1 cycle, same as `out pins, 8`). |
| 16-bit HSPI via FPGA | ~240 MB/s | N/A | Needs FPGA |
| 32-bit HSPI via FPGA (demonstrated) | ~154 MB/s actual | N/A | Needs FPGA |

For ultr4rick at ≤ 400 Hz PRF (6.5 MB/s), serial SPI is sufficient. The 8-bit PIO HSPI path becomes relevant above ~10 MB/s — for example, if PRF is raised to 1 kHz or acquisition windows are extended to >8 KB per pulse.

## SDK and Toolchain Notes

- **Toolchain:** MounRiver Studio (free, WCH's Eclipse-based IDE) or standalone `riscv-none-embed-gcc` with WCH's multilib patches. Standard RISC-V toolchains do not support the `WCH-Interrupt-fast` attribute.
- **EVT package:** Download `CH569EVT.ZIP` from wch.cn. Contains headers, register definitions, USB3 stack examples (`USBSS_*` functions), and HSPI examples.
- **Register name verification:** `R8_HSPI_CFG`, `R32_HSPI_RX_ADDR`, `USBSS->UEP4_TX_DMA` etc. are based on WCH CH569 TRM v1.x and EVT examples. Cross-check against `CH569.h` in the EVT package before building.
- **USB3 stack:** WCH provides a pre-compiled USB3 library (`libUSBSS.a`). The descriptor registration functions (`USB3_SetDeviceDescriptor` etc.) wrap this library. The EVT `USB3Composite` example is the closest reference.
- **Crystal:** CH569 requires a 30 MHz crystal (or 25 MHz on some sub-variants) for USB3 PLL. RC oscillator is USB-disqualifying.
